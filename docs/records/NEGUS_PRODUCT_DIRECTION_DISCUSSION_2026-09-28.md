## 3. 当前产品模型草案

### 三人公司与系统主管

前序总结记录了“三人公司”的原始职责：

1. 产品侧：产品、营销、公关、市场。
2. 技术侧：技术、实现、成本、稳定性、质量。
3. 运营侧：运营、流程、复用、效率。

三者原先作为 Agent 设想，目前是否都保留为 Agent、是否调整仍未确定，交接总结记录的倾向是平级。另有 Negus 系统主管设想，但其与运营助手、用户直接主管、项目经理的关系尚未定案。

### 两种协作语义

- **公开咨询：**当前对话中请相关专业 Agent 回答，用户能看到其意见。
- **后台委派：**交给 Agent 执行可追踪的工作，完成或需要介入时回报。

这两种方式应作为待设计的不同语义保留；不把所有问题都创建成任务，也不预设所有专员回答都必须由主管转述。

### 快速需求判断

用户提出回答前先做快速判断。前序助手进一步建议输出意图、责任维度、是否需要执行、是否多 Agent、建议负责人和置信度，再由主管或系统决定如何响应。

**上述字段和调度流程属于助手建议，并非已经确认的接口设计。**是否独立增加一次模型调用、哪些简单场景跳过、低置信度如何处理、用户是否看到路由提示，都尚待验证。

例：“这个功能是不是很难做？”可能同时涉及技术实现、成本、进度和投入产出。应保留多维判断空间，避免仅靠关键词硬路由。

## 5. 尚未定案及后续讨论问题

1. 系统主管、用户直接主管、运营助手和项目经理是几个角色？如何区分职责？
2. 三人公司是否保持平级？哪些角色长期存在，哪些按任务创建？
3. 专业 Agent 何时直接回答，何时由主管整合？跨领域问题由谁收口？
4. 公开 @ 咨询与后台任务如何切换，怎样防止重复执行和无意义对话？
5. 私聊与群聊共享哪些上下文，如何避免信息孤岛并保持访问边界？
6. 快速判断是否比主管直接判断更省时省钱？如何衡量误路由？
7. 用户行为分析收集哪些数据，如何控制、查看和纠正形成的偏好？
8. 自主测试的隔离、预算、验收及更新确认如何安排？
9. 基础页面、自定义组件和模板复用如何衔接？不按每个任务生成 UI 的边界是什么？
10. 主动汇报的时机和密度，以及后台任务的常驻展示方式如何确定？
11. Codex 兼容仍需承诺哪些能力，如何保持用户工作的连续性？
