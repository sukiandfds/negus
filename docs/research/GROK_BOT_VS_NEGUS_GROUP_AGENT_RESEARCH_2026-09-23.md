# Grok Bot 与 Negus：群聊和多 Agent 交互对比

日期：2026-09-23
对照案例：`docs/research/GROUP_CHAT_ACCEPTANCE_CASES_2026-09-15.md`
Negus 界面依据：当前工作区群聊代码，不是验收案例里的目标稿。

## 结论

建议改 Negus 的群聊和员工管理交互，不建议把 Negus 改成 Grok Bot。

Grok Bot 更接近「一个人的 bot 群」。每个 bot 有自己的电脑，可以并行、在笔记本合上后继续干活。Negus 更接近「一个项目的公共房间」：真人和员工在同一条时间线里，不点名就不会有人接话。两边都还没同时做到验收案例要求的独立意见、后台任务树和项目写回。

Negus 应该借 Grok Bot 的管理方式：员工像联系人一样可打开、可并行、可看见各自的电脑和任务。不要拿掉真人旁听、点名才发言，也不要把员工收成只能互聊的私人 swarm。

## Grok Bot 已确认的用法

用户打开的是一个群聊外形的桌面应用，不是一条单人模型对话。

1. 进入 Grok Bot，而不是 Grok 普通对话或 Grok Build。
2. 看到的是 bot 名单和群聊，不是一个万能输入框。
3. 每个 bot 有自己的电脑，可以进用户的应用和工具里干活。评论者追问登录墙网站时，理解成 X 给 bot 配一台私人云电脑；官方页未能打开，不能把「私人云」三个字写成 FAQ 原文。
4. 多个 bot 并行。笔记本合上以后，任务仍在对方的电脑上继续。
5. 群聊里主要是 bot 对 bot。2026-08-13 的使用者没有找到邀请其他真人进同一群的路径，并认为这和产品的群聊外形不一致。
6. 不能在这里换成 Claude 或 GPT。额度算在 Grok 订阅上。

和 Negus 验收案例的关系：它强在「谁有自己的执行环境、谁可以同时跑、关掉电脑还在跑」。它弱在「真人闲聊时助手旁听」「只点名一个人」「四个角色隔离后再汇总」「把结论写回项目任务」。

## Negus 现在实际怎么点

底部栏三个入口：`桌面`、`会话`、`群聊`。群聊案例都从 `群聊` 进入，对应项目群，不是某个员工的私人会话。

群聊页：

- 顶栏：`打开侧栏`、`按日期查看历史消息`、`分享`。
- 消息区上方是员工名条。点一个名字，就是点名这个员工。名条上有工作中、等候等状态。
- 空群文案写明：直接发言只会留在群里。点上方员工，或用 `@` 点名，对方才会回答。
- 输入栏左侧：附件、`打开能力菜单`、`点名员工`。忙时出现 `停止当前任务`。右侧是 `查看员工上下文规则`，然后是 `发送`；忙着发言时按钮变成 `加入等候`。
- 能力菜单里有 `停止当前任务`，说明是终止当前群聊正在运行和排队的任务，不是只停一个子任务。
- 点消息头像打开 `个人信息`。员工抽屉里有 `发消息`，会离开群、进入该员工单聊；下面是 `推理模型`、`推理强度`，再点 `确认` 或 `取消`。
- 多个人被点名时，消息上显示「按顺序点名了……」。服务端也是按名单顺序跑，前一个结果里如果再 `@` 别人，会追加到后面。
- 失败的系统消息上有 `再让某员工试一次`。没有「从断点继续」和「重新开始」两个独立按钮。
- 没有独立意见轮、后台任务卡、任务会话入口，也没有「转成项目任务 / 风险」按钮。

所以案例文档里的「系统：已创建 4 个独立意见任务」和「任务卡 T-101」目前不是可点击的界面，只是验收目标。

## 按 10 个群聊案例对比

### 案例 1：真人闲聊，助手旁听

Negus：底部点 `群聊`，直接输入周末是否缓一天，点 `发送`。因为没有 `@`，消息只留在群里，员工名条不应变成工作中。这和案例要求一致。

Grok Bot：没有核实到「真人发言、bot 默认旁听」的开关。已确认的形态是 bot 群，不是项目成员闲聊。若只有 bot，这个案例无法按原样发生。

评价：Negus 这一步不要改成 Grok Bot。缺的是可见的「旁听中」，以及明确不会把闲聊写成决策。

### 案例 2：只问一个员工

Negus：点名条上的产品负责人，或点输入栏 `@` 后选择该员工，再点 `发送`。消息显示「点名了产品负责人」。其他人不会因为这句话自动进队列。点该员工头像，再点 `发消息`，则会离开公共群，进入他的单聊；单聊不是案例要求的公共回复。

Grok Bot：多个 bot 可以同时在群里。没有核实到「只让这一个 bot 回答，其他 bot 只看结果」的按钮。并行是产品卖点，反而不利于这个案例。

评价：Negus 的点名方向对。建议保留，并在被点名员工开始工作时，在群里显示一行「其他人不会自动参与」，而不是只靠用户记得规则。

### 案例 3：四个角色独立判断后再汇总

Negus：只能连续点四个名字。界面会写「按顺序点名了……」，后一个员工能看到前一个已经写进群里的话。没有「先不要互相参考」的按钮，也没有四个来源会话的入口。

Grok Bot：FAQ 确认 bot 可以并行，这比 Negus 的顺序执行更接近「同时独立工作」。但没有核实到隔离上下文、禁止互看、再由主持 bot 汇总的操作。并行本身不等于隔离。

评价：这是最值得改的一处。建议在点名多个人之后，发送前出现选择：`按顺序讨论` 或 `分别独立回答`。选独立时，四个员工同时跑，群里先只显示进度，汇总前不把彼此的正文塞进对方上下文；每条结果可点开该员工自己的会话。不要默认改成 Grok Bot 式的自由互聊。

### 案例 4：负责人拆成后台任务

Negus：点开发负责人并发送「检查群聊内测路径」。他在公共群里顺序执行；群里没有 T-101、T-102、T-103 任务卡，也不能从卡片打开子会话。点头像里的 `发消息` 打开的是员工总单聊，不是某个子任务。

Grok Bot：每个 bot 自带电脑且可并行，天然更像「分头去做」。没有核实到「负责人 bot 创建子任务、子结果先回到负责人、不刷屏」的按钮。

评价：建议做任务卡，不建议让每个子任务都变成一个新的群成员。负责人仍是群里的员工；子任务出现在他的回复下面，卡片上有状态、打开和停止。这比再养一排可见 bot 更符合案例。

### 案例 5：同一主题继续用昨天的分助手

Negus：再次 `@市场负责人` 会继续这个员工在本群的长期会话，不会另开一个研究会话。用户看不到「已识别为昨天的 S-201」。模型要在头像抽屉里改，不能按这个研究主题单独指定。

Grok Bot：bot 有自己的持续电脑和线程，合上电脑也还在，续作能力更强。没有核实到「把今天这句话绑定到昨天那个研究 bot」的明确按钮。

评价：Negus 已有「一个员工、一个群、一个长期会话」。缺的是任务级会话。建议市场负责人的回复上提供 `继续这个研究`，点进去仍是昨天那条任务，而不是把他的全部群聊记忆都当成这个研究。

### 案例 6：多个员工协作时的上下文边界

案例原文后半在归档文档里被截断，但架构要求是连续点名时，每个员工只看到自己这一轮之前的内容。Negus 2026-09-22 的实现已按点名消息切边界，后一个点名不会提前进入前一个员工的上下文。

Grok Bot 没有对应的「点名窗口」说明。并行 bot 若共享整个群记录，反而可能互相污染。

评价：Negus 这条规则应保留。界面上建议在「按顺序点名了 A、B」旁边能展开，看到 A 实际读到哪一条为止。

### 案例 7：真人纠正错误理解

Negus：直接在群里发送纠正，再点名员工。纠正和原话都在公共记录里，但没有把「长期记忆已完成」标成错误判断的按钮，也没有版本对照。

Grok Bot：没有核实到事实、判断、纠正三种状态。

评价：两边都没做好。Negus 不必先抄 bot 管理；在引用某条员工消息后，增加 `这是错误判断`，后续点名把这条纠正带上即可。

### 案例 8：停止一个后台任务

Negus：输入栏或能力菜单点 `停止当前任务`。它停的是当前群里正在跑和排队的讨论，不是一张任务卡。停完没有「从断点继续」和「重新开始」。失败后只能点 `再让某员工试一次`。

Grok Bot：bot 并行、各有电脑，理论上可以停其中一个而不影响另一个。没有核实到单个 bot 的停止按钮叫什么。

评价：Negus 应该改。停止按钮要落在某一张任务或某一个员工名条上，而不是整个群只保留一个停止。至少先做成：名条上的员工正在工作时，点该员工可 `停止此人`，其他已点名的人继续。

### 案例 9：会议冲突和待确认

Negus：三名真人直接发言，没有「记录模式」开关。不点名就不会有记录助手插话，因此不会误把「周五上线」写成决定，这一点是安全的。也没有会后 `生成摘要、分歧、待办` 的按钮。

Grok Bot：若群里没有真人，案例不成立。若把记录助手做成一个总会插话的 bot，又会破坏案例 1。

评价：不要加一个默认发言的记录 bot。在顶栏加 `开始记录`，开启后才允许记录助手指出冲突；结束时再点 `生成待确认项`。关闭时回到现在的旁听。

### 案例 10：汇总后写成项目任务和风险

Negus：群里可以看交付物并审核，但消息上没有 `转成项目任务`、`记为风险`。要去项目管理页另行处理，来源链不是从这句话一键带走。

Grok Bot：强项是 bot 在自己的电脑里把事情做完，不是把一句群聊变成带负责人、优先级和来源的项目对象。

评价：这是 Negus 该保持的差异。建议在员工汇总消息上放 `转为任务` 和 `记下风险`，点开时带上原消息和相关员工会话。不要只在 bot 自己的电脑里留一份结论。

## 和桌面案例的关系

`docs/planning/NEGUS_DESKTOP_PRD.md` 里 2026-09-21 的投资人案例 I01–I10、普通用户案例，主要是桌面卡片，不是群聊。只有两则和 Grok Bot 重叠：

- I03 要看见并暂停自动化。Grok Bot 的并行和 24/7 更接近「后台真的在跑」；Negus 仍要求暂停结果可核对，不能只显示一个 bot 在线。
- I05 要看见正在跑的三件事并能点回原任务。Grok Bot 的多 bot 并行符合「不必守着一个窗口」；Negus 桌面如果只链到会话，仍看不到群里的子任务。

其余图片、天气、购物清单等案例，Grok Bot 的群聊和 bot 电脑解决不了，不应拿来改群聊。

## 是否修改

修改，但范围收在群聊的任务和员工管理，不改产品边界。

建议做：

1. 多员工发送前增加 `按顺序讨论` / `分别独立回答`。独立模式并行，且汇总前互不读取。
2. 员工名条上的停止只停这个人；群级 `停止当前任务` 保留为停全部。
3. 负责人回复下挂任务卡，能打开、停止、继续，不把子任务刷成新成员。
4. 汇总消息增加 `转为任务` 和 `记下风险`。
5. 顶栏增加可关闭的 `开始记录`。默认仍是现在的旁听。

明确不做：

- 不把项目群改成只有 bot 的私人 swarm。案例 1、2、7、9 依赖真人。
- 不给每个员工发一台与项目无关的云电脑来替代项目目录。Negus 的执行对象仍是这个项目里的文件和群记录。
- 不把模型锁死成 Grok。员工抽屉里的模型和强度应保留。
- 不把 OpenMausBot 的右键置顶、Teams 导入、频道回应规则照搬进当前群聊。那些按钮没有官方对应证据。

## 验收时看什么

改完后用案例 3、4、8 验收即可判断有没有借对：

- 案例 3：点四名员工，选 `分别独立回答`，群里在汇总前看不到互相引用。
- 案例 4：开发负责人名下出现三张任务卡，中间输出不每步刷屏。
- 案例 8：只停止其中一张，另外两张仍完成；被停止的卡片留下已完成步骤，并有继续或重来。
