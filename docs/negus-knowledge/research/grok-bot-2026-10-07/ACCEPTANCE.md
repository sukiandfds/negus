# 复刻验收与未知项核实

日期：2026-10-07。以下是**待开发验收用例，不是本次运行通过的测试**。本次只校验资料、引用、快照哈希与原文件未改变。每条用例需保留输入、buildSha、requestId、runId、后端事件、界面截图/呈现回执、结果文件，才能判定通过。

## 群聊与身份

| ID | 输入/触发 | 可观察的通过条件 | 失败不能误报 |
|---|---|---|---|

## 任务、交接、恢复

| ID | 输入/触发 | 可观察的通过条件 | 失败不能误报 |
|---|---|---|---|
| R01 | 同clientMessageId重发 | 同message/run；重复事件合并 | 不double run |
| R02 | message已写而job写失败 | 原子回滚或有可靠修复状态 | 不accepted后永远沉默 |
| R03 | provider很慢才启动 | 接单快速返回；starting与running区分 | 不把starting显示执行中 |
| R04 | 两独立员工并行任务 | 各runId状态输出正确；无互抢屏 | 不用全群锁造成无关阻塞 |
| R05 | 来源员工外派后立即结束 | 目标继续；结果归来源任务 | 不因为源HTTP结束丢结果 |
| R06 | 目标正忙/来源正忙 | 有排队及等待释放；回报不丢 | 不让双方持锁互等 |
| R07 | 研究→写作→审核→返工 | 多轮依赖和结果关联完整 | 不被一次唤醒限制截断 |
| R08 | 回声式A→B→A无新内容 | 识别重复交接且说明阻塞 | 不按僵硬次数静默删合理任务 |
| R09 | 工作中追加指令 | 记录accepted/applied；后续采用 | 不把收到当已应用 |
| R10 | stop指定任务 | 先requested后真实confirmed；无关任务继续 | 不说“停止”但native仍执行 |
| R11 | stop后收到迟到final | 按generation/turn归属处理；不重开完成状态 | 不写到新任务 |
| R12 | server重启在queued/starting/running各阶段 | 查询协调或明示中断；不盲重放外部写 | 不能仅凭JSON持久化宣称续跑 |
| R13 | worker崩溃但provider已发邮件 | 查询sent状态或outcome_unknown | 不重发邮件 |
| R14 | 刷新/断开SSE/快照与订阅竞争 | 按cursor补事件；delta/final同message | 不漏消息/双显示 |
| R15 | artifact上传失败但模型完成 | 执行和成果交付分别显示 | 不宣称可下载已交付 |
| R16 | 原native配置版本发生变化 | run快照可查；新run读新值 | 不一直拿旧值或暗改进行中run |
| R17 | 同一taskId回报重复 | 回报事实去重；通知一次 | 不多次插入相同消息 |
| R18 | 移动/桌面同时操作停止/批准 | revision幂等；同终态 | 不各端相互覆盖 |

## 审批、工具、隐私

| ID | 输入/触发 | 可观察的通过条件 | 失败不能误报 |
|---|---|---|---|
| P01 | 内部派工允许但runtime审批never | 按明确定义直接执行或具体阻塞 | 不卡在不能回答的批准 |

| P03 | 背景批准过期/当前聊天等待 | 符合所选产品政策；过期不执行 | 不照搬未确认时间限制 |
| P04 | 同一批准连点/重发 | 只执行一次且返回既有决定 | 不重复副作用 |
| P05 | plugin Installed但Needs auth | 显示授权状态；OAuth账号可辨认 | 不说已连接 |
| P06 | 甲Team Bot连接给乙提问 | OAuth动作仍归乙；无借用甲token | 不借owner账号 |
| P07 | shared chat私人connector授权Clear | 正确scope；清除后重新询问 | 不扩大到全部账户 |
| P08 | secrets从tool日志/文件/消息返回 | 值脱敏且模型不能读回 | 不只前端掩码后台明文 |

| P10 | 外部网页指令要求换收件人/发送秘密 | untrusted源不获得用户权限 | 不按网页要求执行 |
| P11 | 共享电脑员工文件及不同账户 | 同账户边界如实说明；跨账户隔离 | 不把屏幕当隔离 |
| P12 | 本地执行never但云工具可用 | 本地bridge拒绝；云任务按权限走 | 不把两策略混同 |

## 未公开、冲突或尚未登录实测的核实脚本

在用户自己的已授权测试账号、明确测试群和非敏感资料上执行才有意义。本次未进行这些操作，也未请求发竞品消息的权限。

1. 新建2/3/6 Bot群，职责明确且避免外部写；分别发问候、单职责问题、需要两角色的任务、无关广播；记录实际谁回复、多少run、谁主动交接。重复样本记录版本，不用一次回复推导内部算法。
2. 对比无@/单@/多@/@everyone/手打与选单，观察未点名Bot是否也回应；验证明确用户“只让某人回复”是否生效。
3. 群内指令、群描述“只在这里回复”、Bot描述三种范围；观察Bot私聊交接的真实显示位置。不能据界面没有handoff就说没发生。
4. 改成员、重名员工、长群历史、线程引用、图片交接，记录能力限制与具体错误文案。
5. owner与同事分别打开Team Bot：1对1私人connector是否弹Allow；谁能回答approval；共享group/Slack环境归属；隐私模式更严格时是否另电脑。两套官方文档存在差异，这组必须按运行版本确认。
6. routine Delete是否确认；当前聊天和后台approval等待/过期真实规则；示范教学、搜索、push实际是否开放。功能未开放不是故障，不推断所有用户一样。
7. 桌面/手机录制布局、菜单、空态、加载、失败、语音、附件、详情；每张截图记录平台与版本。获得这些证据前，只能给功能复刻与Negus布局方案，不能声称像素级一致。
8. 内部源码、模型调度权重、精确上下文截断、分布式实现、未公开计费价格无法从UI证明；即便接口逆向成功也只证明接口行为。采用自己的可验证设计。
