# 切换模型后，下条消息用谁？

适用：普通单聊、员工主对话。这里记录产品定义；发布与实测记录留在[父条目](item.md)。

<a id="model-pick-01"></a>

## 按渠道选模型

**MODEL-PICK-01 · 现行**。范围：人在普通单聊或员工主对话的输入框主动选模型。历史设置恢复、外部助手改配置不在本条范围。

- **序号：** MODEL-PICK-01
- **功能入口：** 对话输入框 → 配置 → 模型
- **前端文件：** [ModelSettingsControl.tsx](../../../../ui-feishu/shared/features/models/components/ModelSettingsControl.tsx)：visibleModels、stageModel
- **用户原话：** “我觉得目前是符合定义的。也就是说，测试的预期效果不应该是‘预期通过’。”
- **原话日期：** 2026-11-27，本次对话
- **产品预期体验：** 选 B 只看到 B 的模型；A 有同名模型也不会选错渠道。
- **产品逻辑流程：** ① 按配置筛列表；② 选中后保留渠道和模型；③ 发送按所选渠道执行。若直接向普通路由传入该外部配置未登记的模型，应拒绝。
- **涉及文件：** [model-provider-service.mjs](../../../../windows/server/model-provider-service.mjs)：resolveRoute；[路由测试](../../../../windows/tests/cc-switch-config-service.test.mjs)：same model on two channels
- **最后代码更新日期：** 2026-11-19，相关筛选与路由校验逻辑（40788d24）；不计文档或测试改动。
- **助手检查代码评价：** 2026-11-27，按渠道列出同名模型、选 B 路由到 B、拒绝目录外模型的路由测试通过。
- **用户体验评价：** 2026-11-27，用户认可普通选择应拒绝目录外模型。本次未记录从界面发送并收到回复的体验反馈。

**验收：** A、B 配置有同名模型 → 在原窗口选 B 并发送 → 核对实际渠道为 B，原窗口收到回复。路由测试单独核对目录外参数被拒，不替代上述操作。
**澄清：** 2026-11-27 原话“1、2 应该是同一个需求吧？”正常选择与目录未命中归入同一条；同日后续原话（见表）取代此前“是否放行待核对”的表述。

<a id="model-restore-01"></a>

## 恢复历史对话的模型名

**MODEL-RESTORE-01 · 现行定义**。与主动选模型分别维护。

- **序号：** MODEL-RESTORE-01
- **功能入口：** 重新打开已有对话 → 查看最后成功发送的模型；原会话需要接续时恢复已保存的模型设置。
- **前端文件：** [ConversationDetails.tsx](../../../../ui-feishu/src/components/ConversationDetails.tsx)：对话详情从 lastSuccessfulSettings 显示历史模型名。
- **用户原话：** “这个我觉得是合理的。就是保留原来的模型名。行不行你别管。”
- **原话日期：** 2026-11-27，本次对话。
- **产品预期体验：** 原来用 A，后来目录移除 A，历史仍是 A；恢复设置也不替换成当前默认模型。
- **产品逻辑流程：** 读取已保存的配置和模型 → 原样恢复；不以当前目录或供应商是否仍支持该模型作判断。主动选择、再次发送的结果不属于此定义。
- **涉及文件：** [provider-conversation-store.mjs](../../../../windows/server/provider-conversation-store.mjs)：普通对话 ensureRestored 将解析结果传入 resumeProviderSession；[model-provider-service.mjs](../../../../windows/server/model-provider-service.mjs)：resolveRoute 处理目录与默认模型。
- **最后代码更新日期：** 2026-11-27，resolveRoute 删除按目录替换已指定模型的分支。
- **助手检查代码评价：** 2026-11-27，双渠道回归用例先复现 A 被替换为 B；修改后两种渠道都保留 A，未指定模型仍取 B。失败发送不覆盖成功记录的重开测试通过。
- **用户体验评价：** 2026-11-27，用户认可恢复时保留原名、不判断可用性；未记录用户遇到默认模型替换的反馈。

**验收：** 保存模型 A 后将其从目录移除，默认模型设为 B。重开查看历史应显示 A；触发原会话恢复，传给会话的模型也应是 A。两处分别核对，无需向供应商试发。
**后续澄清（2026-11-27）：** “这个时候应该显示这条对话最后成功的模型。” “新建对话才是使用negus默认配置”。两种渠道共用成功记录；有历史值不按目录换模型，取代此前实现中的自动替换。
**澄清：** 本次明确恢复时不判断可用性；补充历史恢复定义，不替代 MODEL-PICK-01 的主动选择规则。

## 员工切换模型｜已有员工主对话

下列编号供派工与验收引用。所有步骤在同一可见员工主对话内；普通单聊弹窗、群聊均不在此流程。这里列产品预期，不作为本轮上线或实测证明。

| 步骤编号 | 用户操作 | 成功条件与反例 | 定义依据 |
| --- | --- | --- | --- |
| EMP-MODEL-01 选模型 | 上轮用 A，只在输入框选 B，再改选 C | 只保存待发送草稿；没有消息、切换提示或新的成功记录。不能在这一步要求员工空闲。 | 下文 11-19 草稿定义；11-26 本次澄清 |
| EMP-MODEL-02 发消息 | 用最后选的模型发送带引用的消息 | 原文立即出现一次。同配置沿用当前运行会话，不显示切换提示；跨配置仍留在员工原窗口，不问是否另开对话。 | 11-19 员工定义与同日澄清 |
| EMP-MODEL-03 等切换 | 跨配置发送后观察时间线 | 独立系统行显示“正在切换至 <模型>…”并转圈；接续成功才改为“已切换至 <模型>”并停转，此时可以仍在等回复。失败显示“模型切换失败”，从原消息重试，不重复显示原文。 | 11-19 同日澄清 |
| EMP-MODEL-04 收到回复 | 询问前轮内容，收到新模型回答，再刷新 | 新模型接得上前文与引用；刷新仍在同一主对话，原文和新回答不丢、不重复。草稿或失败不覆盖上次成功模型。 | 11-19 员工验收原话；下文 11-20 成功记录定义 |

**2026-11-19 用户原话**（[员工主对话切换模型及同日澄清](../FEAT-002/item.md#2026-11-19-员工主对话切换模型)）：

> 我发过去之后，系统立刻提示切换模型，需要稍等片刻，然后转圈加载中

> 切换模型的提示不要放在我的消息的下方，而是类似于系统提示那种

**2026-11-26 用户原话**（本次讨论）：「输入框选新模型，我本来以为只应该是改变前端显示，没有“检查员工是否空闲”这条。不过感觉好像也合理。」这是对现状的提问，不是新增忙碌检查的决定。现行跨配置接续包括后台压缩；是否改用详情一次性交接见文末提议。

## 普通单聊与员工主对话的规则对照

| 操作 | 应看到的结果 |
| --- | --- |
| 上次由 A 成功回复，在输入框选 B，尚未发送 | 输入框显示 B；上次成功回复仍显示 A。改选或查看配置再返回，不发送消息。 |
| 同一配置换模型，然后发送 | 沿用当前对话，不弹跨配置确认框。 |
| 普通对话跨配置，点击发送 | 此时才询问继续当前会话、创建新对话或取消。继续则留在原窗口；创建则打开新对话、保留原对话；取消则原文、附件、引用及所选设置都保留。 |
| 员工主对话跨配置，点击发送 | 直接在原窗口接续，显示切换进度；失败可从原消息重试。 |
| 切换或发送失败，再打开详情 | 草稿或失败不覆盖最后成功的配置；只有新模型成功回复，成功记录才更新。 |

## 用户原话与决定沿革

**2026-11-08｜早期规则**

> 同配置切换的目前就保持不变。不同配置的，就弹出这个提示之后，弹出一个提示框“切换配置将使用完整上下文创建新对话，是否创建？”然后确认的话，就自动切到新对话。取消的话，输入框就恢复上一次的最后发送成功的配置和模型，这个上次最后成功的我们现在应该有记录的。

取消回填、询问时点已被 11-19 替代；普通对话的选项在 11-22 扩充。

**2026-11-12｜记录中的有效决定（非用户逐字原话）**：最后成功使用的模型和下一次准备使用的模型分开保存。

**2026-11-19｜选择是草稿，发送才确认**

> 模型和强度/配置仅本地草稿、断线可选缓存、去铅笔返回保留、收起不加配置名。普通对话跨配置只在发送时询问创建，取消保留草稿；员工跨配置沿用独立系统提示，同配置原生。在途任务/历史/滚动保护。

同条目后续澄清原话：「保留用户现有铅笔入口；点击它查看配置再返回，保留当时选好的配置、模型、等级与输入内容」。这句话替代“去铅笔”。

**2026-11-20｜成功记录的显示**

> 显示最后一次成功发送的配置名称+模型随最新正文更新，历史上旧渠道已删也能显示，失败或草稿不覆盖；发送时检查选中配置，失败不唤醒，保留输入及附件可重试。

**2026-11-22｜普通对话也能原地接续**

用户原话：「普通对话弹窗新增加的选项，继续当前会话的选项，等于现在员工对话中，正在切换至和已切换至的效果。然后他们要共用一个代码文件……这次切换没完成的，也要改成共用代码。」

## 讨论中，不作为上线规则

2026-11-26，本次对话用户原话：「我想的是，用对话详情部分作为我们新对话的上下文，写一次进去就好了。就不压缩了」。“仍在原窗口”是已有定义；用什么内容交接是这次提议，尚待验证。
