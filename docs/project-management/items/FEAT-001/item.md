以下是本次维护对话直接可见的用户原文，收录于2026-10-30；早先发言的精确日期未独立核实。下文8月状态仅是历史记录，不代表当前有效体验。

> 不只是配置列表，其他地方的缓存逻辑应该都要一起排查，我的要求是所有尽量同时加载缓存，加载更新，不要每个部分独立更新。你快检查一下，不确定的和我讨论

- 验收必须观察整个对话各处的时间线，不能只用正文出现或最终截图证明同步。需求已确认不等于当前代码已实现。

#### 实施批 BC1：消息账本字段（修改前）

用户查看任务对话时，已知助手署名和发送编号经过员工消息账本归一化会丢失；原生用户消息的 `clientId` 也未映射到账本发送编号。沿用现有账本写入及读取，仅保留可信调用者提供的 `displaySourceAgentId`、`submissionId`，并将原生 `userMessage.clientId` 映射为 `submissionId`；不从正文推断身份，真人消息不加署名。预计业务1至2文件 +约6至15行、测试1文件 +约25至50行，文档2文件 +约8行；不改员工绑定校验或滚动逻辑，不发布、重启、提交或推送。

#### 实施批 BC2a：普通来源任务底层契约（修改前）

用户让普通对话助手派后台工作时，现有 kernel 入队要求员工 `agentId`，MCP 也没有明确供应商/模型/强度和原任务续派参数，因此普通来源无法安全进入同一任务队列。先将入队校验改为仅 `source.kind=conversation` 的真实普通来源可无员工 ID，并扩展现有工具的可选参数；员工任务规则保持不变。此步只铺底层契约，不开放普通对话工具或声称派工已经可用；风险是未接入 adapter 前参数尚未被执行，后续必须按可信 capability 约束并验证幂等。预计业务2文件 +约20/-约3，测试1文件 +约30/-约0，文档2文件 +约8/-0。后续普通 source adapter、逐条署名和运行数据修复继续实施。

#### 实施批 BC2：普通来源完整派工链路（修改前）

用户在普通主对话要求助手创建或继续后台对话，当前没有该对话的 `negus_handoffs` capability；即便调用工具，服务层还要求真实员工，显式 DeepSeek 选择也可能被默认 VIP 覆盖。后台任务初次及追加输入经 native `userMessage` 回读时，现有首条启发式会误标同 turn 真人输入，结果通知也可能显示为真人。沿用同一 task kernel、MCP 和 queue：服务端按来源 thread、活动 turn 和实际 Provider 绑定能力，记录稳定 input/actor；普通 source 不伪装员工，显式选择优先，续派沿原 thread 并持久核对发送意图；只按 native `clientId`/submission 对应记录装饰单条气泡。用户可创建、续派、查看并收到一次结果；未知来源保持无标签。风险在原生 ID 回传、确认丢失和恢复边界，必须定向验证且不盲重发。预计业务约5至8文件 +约180至320/-约25至60，测试2至3文件 +约120至220/-约10，文档2文件 +约15/-0；不改滚动、内核或运行数据，不发布重启提交推送。
