# Negus 产品与技术协作原则

更新时间：2026-09-23

## 文档目的

Negus 的产品经理负责产品定义、用户场景、预期效果和验收标准。技术实现、数据架构、运行链路和验证方案由开发负责。只有当技术方案无法稳定实现预期体验时，产品经理才需要介入技术链路进行纠偏。

技术实现不能把用户变成技术方案的维护者。开发应先理解产品目标，再选择轻量、可扩展、可复用的实现方式。

## Negus 的核心价值

Negus 不是孤立功能的集合，而是一个可以高效自定义、持续扩展并让功能互相协作的系统。

新增组件、页面或功能都应尽量接入统一的数据、会话、权限和运行链路，使它们能够：

- 复用已有数据和基础能力；
- 与其他功能自然组合和互通；
- 在不破坏现有功能的情况下继续扩展；
- 通过统一的状态、缓存和事件机制保持一致体验。

## 技术方案的三个硬要求

### 可扩展和兼容

实现不能只为当前截图或单一路径服务。需要考虑未来模型、供应商、会话、组件和业务功能的接入，并确认它与现有功能的归属、数据和运行机制兼容。

### 轻量化

优先复用现有能力和真实数据源，减少重复服务、重复状态、额外依赖和人工维护。

避免为了快速出效果而引入孤立桥接方案、重复配置副本或难以维护的脚本。例如，Negus 不应依赖 Python 临时查询来核查本应由 Node 原生服务或共享数据源提供的信息。

### 高效

以真实用户操作链路衡量效率：打开、选择、发送、等待、切换、恢复和继续都应减少等待、空白、重复刷新和无意义步骤。

“代码能运行”“接口返回成功”或“单元测试通过”都不能单独证明用户体验合格。

## 开发工作规则

1. 先读取当前页面、代码、运行状态、已有功能定义和相关历史，再提出方案。
2. 用户已经明确产品目标时，不擅自改写目标，不把技术术语变成新的用户流程。
3. 不擅自增加弹窗、入口、设置项、确认步骤或复杂 UI。
4. 不用技术实现替代用户可理解的交互，也不把内部状态名直接当作产品文案。
5. 不用缓存、临时文件或第二份配置掩盖真实数据源问题；缓存只能加速，不能产生互相矛盾的事实。
6. 不把定向测试、构建通过或代码完成写成真实体验已完成。
7. 真实浏览器、真实供应商、刷新恢复、异常和极端操作顺序需要分别验证。
8. 发现需求、上下文或现状不清楚时，先说明具体不确定点并询问；不得凭猜测开发。
9. 用户要求先观察、先统计或先不改时，只做检查和报告，不修改代码。
10. 用户授权开发后，保持最小改动范围，并说明用户实际会看到的变化、验证证据和遗留风险。

## 验收标准

每个功能至少区分以下状态：

- 产品定义完成；
- 代码实现完成；
- 自动化测试通过；
- 当前运行服务已加载；
- 真实浏览器操作通过；
- 真实供应商或真实数据链路通过；
- 用户实际验收通过。

只有满足对应证据，才能使用相应的完成表述。无法验证时必须明确写出“未验证”，不能用推测或测试结果代替。

## 本次确认的沟通边界

产品经理关注用户体验和最终结果，不应被迫承担技术流程设计。开发需要自行完成架构判断、实现、测试和风险控制；只有在需求确实存在歧义时，才提出具体、必要的问题。

Negus 后续所有功能都以“高效自定义、轻量实现、良好兼容、相互互通”为判断基础，不为了展示局部效果而采用短期、孤立、难扩展的方案。
